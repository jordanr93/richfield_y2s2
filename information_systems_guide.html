  • Payback period: how long benefits or savings take to recover the investment.

2.7-2.9 Technology, Security, Responsive Design and Prototyping

  • Output channels: screens, printed documents, internet delivery, email, messaging, wireless devices, digital audio/images/video and specialised devices. Select according to user, timing, portability, confidentiality and accessibility.
  • Input choices: batch input suits accumulated work; online input suits immediate interaction. Automated capture improves speed but still requires validation and controls.

3.4-3.5 Data Terms, Integrity and Entity-Relationship Diagrams

View Data Terms and Integrity View Entity-Relationship Diagrams ↓

ConceptOperational meaning
EntityA person, place, thing, event or concept about which data is stored.
AttributeA characteristic describing an entity; represented as a field/column.
Primary keyThe minimal field or field combination that uniquely identifies each row.
Foreign keyA field that stores the primary-key value of a related table.
Referential integrityA foreign-key value must match an existing primary key, unless a permitted null represents no relationship.
CardinalityThe number and optionality of instances participating in a relationship.
Relationship visual: CUSTOMER 1 ---- M ORDER 1 ---- M ORDER_LINE M ---- 1 PRODUCT. ORDER_LINE resolves the many-to-many relationship between ORDER and PRODUCT and can store relationship facts such as quantity and selling price.

ERD method: extract nouns as candidate entities, identify business events, assign keys, connect relationships, label cardinality/optionality, resolve every M:N relationship with an associative entity, then validate the model against realistic transactions and business rules.

3.6 Normalization Stages

View Normalization View the Full Worked Example ↓

StageQuestion to askAction
UNF to 1NFAre there repeating groups or multi-valued fields?Make values atomic and place repeating groups in rows or a related table.
1NF to 2NFWith a composite key, does a non-key field depend on only part of it?Move partial dependencies to a table where that determinant is the key.
2NF to 3NFDoes a non-key field depend on another non-key field?Move transitive dependencies to their own table and retain a foreign key.

Quick example: ORDER_LINE(OrderNo, ProductNo, OrderDate, ProductDescription, SupplierNo, SupplierName, Quantity). The composite key is OrderNo + ProductNo. Move OrderDate to ORDER; move product facts to PRODUCT; move SupplierName to SUPPLIER. Keep ORDER_LINE for facts depending on the complete order-product combination.

Why normalize: reduce redundancy and prevent insertion, update and deletion anomalies. Always state the problem removed at each step.

Chapter 1: Development Strategies

Development strategy is about choosing the most suitable way to acquire or build software while balancing requirements, cost, risk, web integration, staffing, and long-term support.

Chapter 1

1.1 Traditional vs Web-Based Systems

1.1.1 Traditional development

Traditional systems are designed to function within specific hardware and software environments. They usually depend on company-controlled infrastructure, LAN/WAN resources and existing legacy systems. Internet resources may be used as enhancements, but the core system remains tied to a defined technical environment.

1.1.2 Web-based development

Web-based systems use the web as a central platform. They are generally more scalable, less dependent on specific hardware, easier to access across different devices and well suited to outsourced operation and support. Web 2.0 adds collaboration, information sharing and social-networking capabilities.

1.2 Evolving Trends

Web 2.0, cloud computing, mobile devices, SaaS, and web-hosted software expanded the acquisition choices available to organizations. The analyst must understand how each trend changes cost, control, scalability, and maintenance.

Web 2.0

Web 2.0 platforms emphasise collaboration, information sharing, user participation and social networking rather than one-way publishing.

Cloud computing

Cloud computing allows companies to access software and data over the internet through powerful shared infrastructure, reducing the need for in-house servers and resources.

  • SaaS: applications are provided as services, reducing installation and maintenance work for the customer.
  • Mobile and web platforms: increase access needs and raise compatibility, security, and interface concerns.

1.3 In-House Software Development Options

Section 1.3 is a decision set, not one single option. The study guide compares making software, buying a package, customizing it, and creating user applications.

1.3.1 Make-or-buy decision

Compare developing a custom system with purchasing a commercial package. Consider total cost of ownership, business fit, implementation time, available skills, integration and long-term support. A horizontal application serves many industries; a vertical application targets a specialised industry. A value-added reseller (VAR) customizes commercial software for a particular customer or market.

1.3.2 Developing software in-house

In-house development may be appropriate when a company wants to:

  • Satisfy unique business requirements that commercial software cannot meet.
  • Minimize changes to existing business procedures and policies.
  • Meet constraints imposed by existing systems and integration requirements.
  • Meet constraints imposed by existing hardware, software or legacy technology.
  • Develop internal IT resources and capabilities for long-term support.

1.3.3 Purchasing a software package

Buying a commercial package can provide the following benefits:

  • Lower initial development costs because the package is sold to multiple customers.
  • Less time to implement because the software has already been designed, programmed, tested and documented.
  • Proven reliability and performance benchmarks when the product has an established user base.
  • Less need for technical development staff.
  • Future upgrades and enhancements provided by the vendor.
  • Useful input from other companies that already use the package.

Balance these benefits against process disruption, retraining, integration and total-cost effects.

1.3.4 Customizing a software package

  1. Purchase a basic package with vendor customization: select optional modules or add-ons that the vendor provides.
  2. Negotiate directly with the vendor for enhancements: pay the vendor to change or extend the package.
  3. Purchase the package and modify it internally: make permitted changes using internal analysts and programmers.

Additional considerations: vendor customization can increase cost and delivery time, while internal changes can make future upgrades and support more difficult.

1.3.5 Creating user applications

Users may create smaller solutions with productivity software such as spreadsheets or word processors. This can reduce the IT backlog and empower users, but it still requires training, support, security, data-integrity controls and clear limits on access to corporate data.

The systems analyst's role changes by option: deeper design and testing involvement for in-house work, more vendor evaluation and contract/support focus for packages and outsourcing.

  • Application Service Providers (ASPs): rent access to an operational software application, commonly through a subscription or usage fee.
  • Internet Business Services (IBS): provide hosted web-based support for transactions such as order processing, billing and customer relationship management.

1.7 Selecting a Development Strategy

The systems analyst helps management compare outsourcing, in-house development, packaged software, user applications or a combination. In-house development requires deeper involvement in design, testing and implementation; outsourcing and commercial packages shift more of that work to the vendor. Include users and relevant IT staff in the evaluation team, compare total cost of ownership, and rule out alternatives that do not meet requirements.

1.7.1 The systems analyst's role

Analyse requirements, costs, benefits, risks and future needs, then present a recommendation that management can approve.

1.7.2 Cost-benefit analysis

TCO is the key selection factor because it includes initial development or purchase cost plus long-term maintenance, support, upgrades, training and operating costs. Use payback analysis, return on investment (ROI) and net present value (NPV) to compare alternatives.

1.7.3 Cost-benefit checklist

List alternatives, identify when costs and benefits occur, allow for growth, include support and licensing costs, apply the financial tools, and report the results.

1.8 The Software Acquisition Process

The five-step acquisition process turns requirements into a justified acquisition decision:

  1. Evaluate requirements: identify features, network and web issues, future volume and hardware, software and personnel constraints; prepare an RFP or RFQ.
  2. Identify vendors or outsourcing options: investigate vendors, consultants, industry sources, forums and current users.
  3. Evaluate alternatives: compare proposals, demonstrations, tests, references, benchmarks and weighted evaluation models.
    • Existing users: ask current customers about reliability, performance, support and implementation experience.
    • Application testing: test important features and workflows against the organisation's requirements.
    • Benchmarking: measure performance under realistic transaction volumes and workloads.
  4. Perform cost-benefit analysis: include licensing, support, maintenance, training, staffing, customization, transaction fees and TCO.
  5. Prepare a recommendation: present costs, benefits, risks, limitations and the best-fit option to management before implementation planning begins.
RFP versus RFQ: an RFP asks vendors how they will meet a business requirement; an RFQ is used when the product or service is known and comparable pricing is required.

1.9 Completion of Systems Analysis Tasks

  • 1.9.1 System requirements document: the output of systems analysis, containing detailed specifications, requirements, alternatives, recommendations and cost and time estimates.
  • 1.9.2 Presentation to management: communicates the findings, financial case, risks and recommended direction so management can decide whether to proceed, modify the current system, purchase or customize software, or stop the project.
  • 1.9.3 Transition to systems design: hands the approved requirements and decisions to the design phase and provides the basis for implementation planning.

Worked Example: Choosing Software for an Order System (supports 1.7-1.9)

Scenario: a company wants a new order processing system. A website is expected to increase orders by almost 80%, but the company also has legacy accounting software and limited internal programmers.

  1. Evaluate requirements: list required features, web access, network/intranet needs, data exchanged with customers or vendors, expected growth, and hardware/software/personnel constraints.
  2. Prepare an RFP or RFQ: use an RFP if vendors must propose how they will satisfy the requirement; use an RFQ if the exact product/service is already known and pricing is needed.
  3. Identify vendors or outsourcing options: use vendor sites, industry trade sources, consultants, forums, and references from existing users.
  4. Evaluate alternatives: compare package features against the RFP, ask existing users, run application tests, and use benchmarks for volume-sensitive performance.
  5. Perform cost-benefit analysis: include licenses, support, maintenance, training, volume-based fees, staffing, customization, and what-if scenarios.
  6. Recommend: present costs, benefits, advantages, disadvantages, and the option that best fits strategy and risk.

Chapter 1 Key Points

  • Traditional versus web-based systems: traditional systems are tied more closely to defined hardware, software and legacy environments, while web-based systems are more scalable and suited to distributed or outsourced operation.
  • Cloud computing and SaaS: both provide internet-based access; cloud computing focuses on shared infrastructure, while SaaS provides hosted application functionality.
  • Development choices: in-house development offers business fit and control, while commercial packages can be cheaper, faster and supported by vendor upgrades.
  • Outsourcing and offshoring: these can reduce cost or provide expertise, but introduce control, security, communication, cultural and provider-dependence risks.
  • Systems analyst's role: involvement is deeper for in-house development and shifts toward evaluation, contracts and support when vendors provide the solution.
  • TCO and financial analysis: compare long-term costs, not only the initial price, using TCO, payback, ROI and NPV.

  • Requirements document: records the analysed requirements, alternatives, recommendations, costs and time estimates that support management approval and transition to design.

2.1 User Interfaces and 2.2 Human-Computer Interaction

A user interface is the hardware, software, screens, menus, functions, outputs, and features that support communication between user and computer. HCI focuses on making that interaction productive, learnable, and user-friendly.

Modern UI design starts from user needs and business goals, not from printed outputs alone. The best interfaces often feel invisible because users can complete tasks naturally.

2.7 Technology Issues

2.7.1 Output technology

Output channels include internet-based delivery, email, blogs, instant messaging, wireless devices, digital audio/images/video, automated fax, podcasts, computer output to digital media (CODM), and specialised output forms.

2.7.2 Input technology

Compare batch input with online input. Online input is used in point-of-sale (POS) terminals, ATMs, factory workstations, hospitals, retail stores and libraries. Select between them based on timeliness, volume, error handling, cost and operational needs.

2.8 Security and Control Issues

2.8.1 Output security and control

Protect reports and other output through key control methods, secure distribution and storage, safe disposal, access restrictions and IT department oversight. Diskless workstations can reduce the risk of local data being retained on user devices.

2.8.2 Input security and control

Use audit trails, controlled handling of source documents, data security policies, audit-trail files and reports, protection from unauthorised access, and encryption of sensitive data.

2.9 Emerging Trends

2.9.1 Modular design

Modularity supports flexibility, team collaboration and easier maintenance.

2.9.2 Responsive web design

Responsive layouts combine CSS3, flexible images and fluid grids so content adapts to different screen sizes and devices.

3.1 Data Design Concepts

3.1.1 Data Structures

A data structure organizes, stores, and manages data. File-oriented systems store separate files, which can create redundancy and inconsistency. A database uses connected tables as an overall data structure.

3.1.3 Database Management Systems

A DBMS provides tools and interfaces for adding, updating, managing, accessing and analysing data. Its benefits include scalability, economies of scale, enterprise-wide applications, stronger standards, better security and data independence.

3.2 DBMS Components

3.3 Web-Based Design

3.6 Normalization Stages

3.6.1 Standard notation and unnormalized design

Use standard notation to show primary keys and attributes. Identify repeating groups and mark the original unnormalized table before decomposing it.

Normal formRule
1NFNo repeating groups.
2NFIn 1NF and every non-key field depends on the whole primary key.
3NFIn 2NF and no non-key field depends on another non-key field.

3.6.2 First Normal Form

Remove repeating groups and keep each field atomic.

3.6.3 Second Normal Form

Remove partial dependencies so every non-key attribute depends on the whole key. This addresses cumbersome updates, inconsistent data, difficulty adding a product and accidental loss of product information when deleting a record. Check whether other anomalies remain after conversion.

3.6.4 Third Normal Form

Remove transitive dependencies. This prevents repeated supplier details, inconsistent supplier data, difficulty adding a supplier and loss of supplier information when deleting a related product or order.

3.6.5 Two Real-World Examples

Crossroads College: begin with a STUDENT table containing a repeating group of courses, convert it to 1NF using Student Number + Course Number, split student/course/grade facts to reach 2NF, then move advisor name and office into ADVISOR to remove the transitive dependency and reach 3NF. GRADE becomes the associative entity between STUDENT and COURSE.

Magic Maintenance: use the service company's seven linked tables as a larger real-world illustration of normalized customer, technician and service-call data sharing common keys.

Normalization refines table design to reduce redundancy, update problems and data inconsistency.

3.7 Codes

Codes use letters or numbers to represent data. They can speed entry, reduce storage, cut transmission time, reveal information, or conceal information. The study guide groups them into sequence, block sequence, alphabetic, significant-digit, derivation, cipher and action codes.

3.8 Data Storage and Access

Storage and access design covers strategic tools for using organisational data, the distinction between users' logical view and its physical implementation, suitable data formats and the treatment of date fields.

3.8.1 Tools and Techniques

  • Data warehousing: integrates data from multiple organisational systems—such as orders, inventory and payroll—so it can be analysed together to support management decisions.
  • Data mart: a smaller, focused collection for a particular department. Its narrower scope can make access faster and more relevant to that department.
  • Data storage and access: storing large volumes requires planned architecture and structure, regardless of whether the organisation uses a warehouse or a mart.
  • Data mining: software searches data for meaningful patterns and relationships. The guide's examples include customer-purchase patterns and market-basket analysis; clickstream use also raises privacy and ethical concerns.
  • Logical vs. physical storage: logical storage is the user's view of fields and records; physical storage is how hardware and the operating system place and retrieve binary data on media. Allocate field sizes for anticipated values without waste.
  • Data coding: computers represent information with bits. The guide covers EBCDIC, ASCII, binary and Unicode: binary stores numeric values efficiently, while Unicode supports a broad range of multilingual characters.
  • Storing dates: a four-digit-year ISO format (YYYYMMDD) avoids the two-digit-year problem and sorts chronologically. For date arithmetic, an absolute date counts the days from a chosen base date; subtracting two such values gives the interval.

3.9 Data Control

File and database management must keep stored data accurate, complete and protected, including the physical security of the system and controls over input and output. A well-designed DBMS provides security and integrity features such as subschemas, passwords, encryption, audit-trail files, and backup and recovery procedures. The analyst ensures these controls are used correctly.

Expanded example: 3.1.2 Mario and Danica

The guide's auto shop example is a clean way to remember why relational databases matter. Mario stores mechanic and job data in two separate file-oriented systems. Because Mechanic No, Name, and Pay Rate are duplicated, one file can show Jim Jones at one rate and another file can show a different rate. The issue is not just storage waste; it is data quality and integrity.

Danica uses a DBMS with two related tables joined by a common field, Mechanic ID. The pay rate appears in only one place, while the common field connects the mechanic table to the job table. This is the basic idea of the relational model: tables are separate, but meaningful relationships allow them to work together.

Exam trap: cohesion and coupling are not opposites. You want high cohesion inside a module and loose coupling between modules.

Related modelling topics: OOA, Classes and Object Relationships (supports 5.4)

Object-oriented analysis organises a system around objects that combine data and behaviour. A class defines attributes and methods; an object is an instance of a class; and relationships show how objects collaborate to carry out business functions.

Related modelling topics: Sequence Diagrams and Business Process Modelling

A sequence diagram visualises event-driven interaction in time order. Lifelines represent actors or objects, and messages show the requests and responses passed between them. The guide identifies sequence diagrams alongside class, state transition and activity diagrams as key object-oriented design documents.

Worked Example: Planning a Payroll System Changeover (supports 5.6-5.9)

Scenario: a payroll replacement passed system testing. Management must decide how to install it, convert data, train staff, and evaluate success.

  1. Separate environments: keep the operational environment for live data separate from the test environment used for testing and training practice.
  2. Choose changeover: direct cutover is cheapest but riskiest; parallel operation is safest but expensive; pilot tests in one location/group; phased introduces one module or function at a time.
  3. Convert data: move existing employee, payroll, tax, and benefits data into the new format, then validate accuracy before live use.
  4. Train people: identify users, managers, and IT staff; choose vendor, outside, or in-house training; use group sessions, hands-on practice, manuals, tutorials, webinars, podcasts, and previous trainees.
  5. Evaluate after implementation: review output accuracy, user satisfaction, reliability, maintainability, controls, security, platform performance, database implementation, IT team performance, documentation, training, cost-benefit estimates, and schedules.
  6. Report to management: include final documentation, evaluation results, unresolved issues, planned maintenance, and recommendations.
Exam trap: training is not a one-line afterthought. The guide says the right people need the right training at the right time, and training plans should be considered early while documentation is created.

Worked Example: Recovering and Retiring an Ageing System (supports 6.4-6.8)

Scenario: an old inventory system has rising corrective maintenance, slow reports, repeated outages, and users asking for web access. A power failure damages a server during peak trading.

  1. Business continuity: use the disaster recovery plan to identify roles, emergency actions, damaged equipment, recovery sequence, and communication responsibilities.
  2. Backup and recovery: restore data from approved backups, follow retention rules, verify the latest clean copy, and test restored data before normal operations resume.
  3. Performance review: measure response time, throughput, turnaround time, workload, and capacity to see whether the system can still support business needs.
  4. Maintenance classification: fix the outage as corrective maintenance, improve slow reports as perfective maintenance, add web access as adaptive maintenance, and reduce future failure through preventive work.
  5. Retirement decision: rising maintenance, expensive changes, user demands, new technology, poor support for new requirements, and declining value indicate that replacement planning should begin.
Strong exam answer: keep recovery and retirement separate. Recovery restores operations after disruption; retirement is the planned end of a system's useful life.
